# Spec 001: Create a booking

- **Status:** Accepted
- **Related ADRs:** 0002 (architecture), 0003 (scope boundaries), 0004 (no overlaps via
  exclusion constraint)

## Summary

A user books a room for a time range. The booking is confirmed immediately. Two
confirmed bookings for the same room must never overlap, including when the requests
arrive at the same time.

## Requirements

### API

**`POST /bookings`** creates a booking for the user identified by `X-User-Id`.

Request body:

```json
{
  "room_id": "3f1c2a9e-8b4d-4e2f-9a6c-1d2e3f4a5b6c",
  "start": "2026-10-20T10:00:00+02:00",
  "end": "2026-10-20T11:00:00+02:00"
}
```

On success it returns `201 Created`, a `Location: /bookings/{id}` header and the
booking:

```json
{
  "id": "9b2e7c41-5d3a-4f8e-b1c6-7a0d2e4f6b8c",
  "room_id": "3f1c2a9e-8b4d-4e2f-9a6c-1d2e3f4a5b6c",
  "user_id": "c5a8d1f3-2e7b-4c9a-8d6f-0b1e3a5c7d9e",
  "start": "2026-10-20T08:00:00Z",
  "end": "2026-10-20T09:00:00Z",
  "status": "confirmed"
}
```

**`GET /bookings/{id}`** returns `200 OK` and the booking, in the same shape, if it
belongs to the user identified by `X-User-Id`.

All error responses use Problem Details (RFC 9457).

### Rules

1. **Identity.** `X-User-Id` must be present, must be a UUID and must match a seeded
   user, otherwise `401`. A malformed header is treated like an unknown user: it
   identifies nobody.
2. **Room.** `room_id` is a UUID and must match a seeded room, otherwise `404`
   (`RoomNotFound`). A value that is not a valid UUID is rejected with `422`.
3. **Time format.** `start` and `end` are ISO 8601 datetimes with an explicit UTC
   offset. A datetime without an offset is rejected with `422`. Times are stored and
   returned in UTC. There is no slot granularity: any minute is valid.
4. **Valid range.** `start` must be strictly before `end`, otherwise `422`
   (`InvalidTimeRange`).
5. **Future only.** `start` must be strictly after "now", as given by the `Clock`
   port, otherwise `422` (`BookingInPast`).
6. **No overlaps.** The range is half-open `[start, end)`. A booking is rejected with
   `409` (`SlotUnavailable`) if it overlaps a **confirmed** booking for the same room.
   Cancelled bookings do not block a slot.
7. **Database guarantee.** Rule 6 is enforced by a PostgreSQL exclusion constraint on
   `(room_id, period)` where `status = 'confirmed'`. The service pre-checks overlaps to
   return a clear error, but the constraint is the real guarantee: the Postgres adapter
   maps SQLSTATE `23P01` to `SlotUnavailable`.
8. **Visibility.** `GET /bookings/{id}` returns `404` both when the booking does not
   exist and when it belongs to another user. An `{id}` that is not a valid UUID is
   rejected with `422`.

### Data

- All identifiers (rooms, users, bookings) are UUIDs. Booking ids are generated by the
  application when the booking is created.
- Rooms and users are seed data, created by a migration. In the acceptance criteria,
  "room 1", "room 2", "user A", "user B" and "booking X" are labels, not ids.
- A booking has: `id`, `room_id`, `user_id`, `period` (`tstzrange`, bounds `[)`) and
  `status` (`confirmed` or `cancelled`). New bookings are always `confirmed`.

## Edge cases

- Back-to-back bookings (10:00–11:00 and 11:00–12:00) in the same room do not overlap.
- A booking fully inside, fully containing, or partially overlapping an existing one is
  rejected.
- The same time range in a different room is allowed.
- A booking with `start == end` is rejected as an invalid range.
- A booking with `start == now` is rejected as in the past.
- Offsets other than UTC are accepted and normalized: `10:00+02:00` and `08:00Z` are the
  same instant and therefore overlap.
- Many concurrent requests for the same or overlapping slots: exactly one succeeds.

## Out of scope

- Maximum duration and per-user booking limit (spec 003). In this spec a user may hold
  any number of bookings, including overlapping ones in different rooms.
- Cancellation (spec 002). Cancelled bookings needed by tests are inserted directly
  through the repository.
- `Idempotency-Key` (spec 004).
- Listing bookings.

## Acceptance criteria

### Creating a booking

**AC-01: A free slot is booked**
- **Given** room 1 has no bookings
- **When** user A books room 1 from 10:00 to 11:00 tomorrow
- **Then** the response is `201` with a `Location` header, and the booking is
  `confirmed`, belongs to user A and has the requested times in UTC

**AC-02: An overlapping booking is rejected**
- **Given** room 1 has a confirmed booking from 10:00 to 11:00
- **When** a user books room 1 from 10:30 to 11:30
- **Then** the response is `409` and no booking is created

**AC-03: A booking contained in an existing one is rejected**
- **Given** room 1 has a confirmed booking from 10:00 to 12:00
- **When** a user books room 1 from 10:30 to 11:00
- **Then** the response is `409`

**AC-04: Back-to-back bookings do not overlap**
- **Given** room 1 has a confirmed booking from 10:00 to 11:00
- **When** a user books room 1 from 11:00 to 12:00
- **Then** the booking is created

**AC-05: The same slot in a different room is allowed**
- **Given** room 1 has a confirmed booking from 10:00 to 11:00
- **When** a user books room 2 from 10:00 to 11:00
- **Then** the booking is created

**AC-06: A cancelled booking does not block the slot**
- **Given** room 1 has a cancelled booking from 10:00 to 11:00
- **When** a user books room 1 from 10:00 to 11:00
- **Then** the booking is created

**AC-07: Different offsets for the same instant overlap**
- **Given** room 1 has a confirmed booking from 08:00Z to 09:00Z
- **When** a user books room 1 from 10:00+02:00 to 11:00+02:00
- **Then** the response is `409`

### Validation

**AC-08: End must be after start**
- **Given** any room
- **When** a user books it with `start` equal to or after `end`
- **Then** the response is `422` and no booking is created

**AC-09: A booking cannot start in the past**
- **Given** the clock says 2026-10-20T10:00Z
- **When** a user books a slot starting at 2026-10-20T10:00Z or earlier
- **Then** the response is `422` and no booking is created

**AC-10: Malformed input is rejected**
- **When** a user sends any of:
  - `start` or `end` without a UTC offset;
  - a `room_id` that is not a valid UUID;
  - `GET /bookings/{id}` with an `{id}` that is not a valid UUID
- **Then** the response is `422` and no booking is created

**AC-11: An unknown room returns 404**
- **When** a user books a `room_id` that is a valid UUID but matches no room
- **Then** the response is `404`

**AC-12: A missing or unknown user returns 401**
- **When** a request has no `X-User-Id` header, one that is not a valid UUID, or one
  that matches no user
- **Then** the response is `401`

**AC-13: Errors use Problem Details**
- **When** any of the errors above is returned
- **Then** the body is `application/problem+json` with at least `type`, `title` and
  `status`

### Reading a booking

**AC-14: A user reads their own booking**
- **Given** user A has booking X
- **When** user A requests `GET /bookings/{X}`
- **Then** the response is `200` with the booking

**AC-15: Another user's booking is not visible**
- **Given** user A has booking X
- **When** user B requests `GET /bookings/{X}`
- **Then** the response is `404`, the same as for a booking that does not exist

### Database guarantee and concurrency

**AC-16: The database rejects an overlap even without the domain check**
- **Given** room 1 has a confirmed booking from 10:00 to 11:00
- **When** an overlapping confirmed booking is inserted directly through the Postgres
  repository, bypassing the service pre-check
- **Then** the repository raises `SlotUnavailable`

**AC-17: Concurrent requests for the same slot: exactly one wins**
- **Given** room 1 has no bookings
- **When** 50 threads, each with its own connection, start together (`threading.Barrier`)
  and book room 1 from 10:00 to 11:00
- **Then** exactly 1 request succeeds, the other 49 fail with `SlotUnavailable`, and the
  database holds exactly 1 confirmed booking for that room

**AC-18: Concurrent overlapping (not identical) requests: exactly one wins**
- **Given** room 1 has no bookings
- **When** 50 threads start together and each books a different range in room 1, all
  of which overlap a common instant
- **Then** exactly 1 request succeeds and the database holds exactly 1 confirmed
  booking for that room
